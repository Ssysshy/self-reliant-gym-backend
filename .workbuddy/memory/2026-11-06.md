## 更正：依赖拉不下来的真实原因（此前判断有误）

- 早前结论「本机连不上 proxy.golang.org」**不准确**。实测在容器内（走宿主机网络）访问 proxy.golang.org 返回 200 OK（0.17s），宿主机网络是通的。
- 失败只发生在我的沙箱 shell：环境注入了 `HTTPS_PROXY=http://127.0.0.1:50875`（sandbox 代理），该代理对 proxy.golang.org 返回 502 Bad Gateway，所以 go 报 "Bad Gateway" 而非 timeout。
- XZchat 之所以「能连」：它根本不用连。依赖早在 2026-10-31 20:20 下载进共享缓存 `~/go/pkg/mod`，`GOPROXY=off go build ./...` 可成功。
- gym 项目缓存未命中的原因：版本号与 XZchat 不同（mimetype 1.4.12 vs 1.4.8、crypto 0.40.0 vs 0.43.0、protobuf 1.36.9 vs 1.36.10 等），必须联网下载才补齐。
- GOPROXY=goproxy.cn 对用户本机非必需（宿主机可直连官方代理），保留仅因国内更快，可 `go env -u GOPROXY` 还原。

## 修复迁移重复执行（Duplicate column 'aux_muscles'）

真因在 `migrations/run.go`：`conn` 是 Connection 固定的会话，`conn.Table(...).Where(...)` 会**累加** Where 条件。
实际 SQL 变成 `WHERE name='001' AND name='002'`，因此从第二条迁移起 count 恒为 0，每次启动都重跑 002/003。
首次建库时不暴露（本来就没跑过），第二次启动重跑 ALTER 就报 1060。与 MySQL 版本、库状态均无关。

修复：
1. `run.go` 改为每次查询用独立会话 `conn.Session(&gorm.Session{}).Table("schema_versions")`。
2. `002_teaching_media.sql` / `003_plan_operation.sql` 改为幂等：查 information_schema 后按需 ALTER（列/索引分别判断），用 PREPARE 执行，中断后可自愈。

验证（临时库 gym_mig_a/c，已删除）：
- 全新库首次启动：3 条迁移全应用，无报错
- 同一库连续三次启动：0 报错，记录数稳定为 3
- 半成品库（仅 001 + aux_muscles）：自动补齐 image_url/mistakes 和所有记录，无报错
- 真实 gym 库连续两次启动：接口 200，数据 8 动作/3 模板/3 套餐未变
